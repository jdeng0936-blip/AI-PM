# V2.6 Deletion Governance

V2.5 把软删除扩展到了 6 类业务对象。V2.6 的目标是把这些散点行为收敛为统一治理层:

- 每次批量软删形成一条可追踪的删除历史。
- 恢复、过期、硬删清理可以基于同一张表治理。
- 30 天硬删先走 dry-run,确认级联影响后再切真实删除。

## Scope

纳入 deletion history:

- `daily_reports.deleted_at`
- `projects.deleted_at` 仅临时工单项目
- `sprint_tasks.deleted_at`
- `risk_alerts.deleted_at`
- `knowledge_items.deleted_at`

不纳入 deletion history:

- `project_members.left_at`: 这是成员退场/RBAC 收敛,不是删除。
- `users.is_active`: 这是账号启停状态,不是删除。

## FK Impact

| 表 | 外键来源 | ondelete 行为 | 30 天硬删影响 |
| --- | --- | --- | --- |
| `projects` | `daily_reports.project_id -> projects.id` | `SET NULL` | 临时项目硬删后,日报保留但失去项目关联。清理前 dry-run 应统计受影响日报数。 |
| `sprint_tasks` | `daily_reports.sprint_task_id -> sprint_tasks.id` | `SET NULL` | 任务硬删后,日报保留但失去主任务关联。燃尽历史快照不依赖 task FK,但日报详情会少任务名。 |
| `daily_reports` | `risk_alerts.report_id -> daily_reports.id` | `CASCADE` | 日报硬删会级联删除对应 RiskAlert。V2.6 Stage 3 dry-run 必须显式统计级联预警数。 |
| `projects` | `knowledge_items.project_id -> projects.id` | `SET NULL` | 项目硬删后,知识条目保留但失去项目关联。 |
| `projects` | `project_members.project_id -> projects.id` | `CASCADE` | 项目硬删会删除成员关系。仅临时项目进入软删硬清理路径。 |
| `sprints` | `sprint_tasks.sprint_id -> sprints.id` | `CASCADE` | 当前 V2.6 不硬删 sprint,所以不会从 sprint 侧级联任务。 |

结论:Stage 4 不应直接无观察期地 `DELETE WHERE deleted_at < now() - interval '30 days'`。先执行两周 dry-run,每天记录将清理对象数量和级联/解绑影响,再决定是否切真删。

## Deletion History Schema

`deletion_history` 采用一条批量操作对应一条历史记录:

- `actor_id`: 执行软删的人。
- `table_name`: 业务表名。
- `record_ids`: 本次批量软删命中的 UUID 列表(JSONB array,字符串形式)。
- `deleted_at`: 软删发生时间。
- `expires_at`: 默认 `deleted_at + 30 days`。
- `restored_at` / `restored_by`: 批次恢复信息。
- `hard_deleted_at`: 过期硬删清理完成时间。

这样 UI 可以按"删除批次"提供最近删除、撤销和过期提示,与 V2.4/V2.5 的 toast 撤销心智保持一致。
